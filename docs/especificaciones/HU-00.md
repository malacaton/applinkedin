## 1. Objetivo

Dejar una solución .NET 10 vacía de negocio pero completa en estructura: compila, ejecuta pruebas y pasa la integración continua. Las historias HU-01 a HU-08 solo añaden código dentro de esta estructura, sin reorganizarla.

## 2. Estructura

El back cuelga directamente de `back/` y el front (v2) de `front/`, sin carpeta intermedia con el nombre del proyecto.

```
applinkedin/
├── global.json                      Fija el SDK de .NET 10 (válido para todo el repositorio)
├── back/
│   ├── Ali.slnx                     Solución (formato .slnx, por defecto en .NET 10)
│   ├── Directory.Build.props        Propiedades comunes a todos los proyectos .NET
│   ├── src/
│   │   ├── Ali.Core/                Biblioteca: núcleo (catálogo, cadencias, huecos)
│   │   ├── Ali.Cli/                 Ejecutable de consola: CLI
│   │   └── Ali.Mcp/                 Ejecutable de consola: servidor MCP (stdio)
│   └── tests/
│       └── Ali.Core.Tests/          Pruebas del núcleo (xUnit v3)
├── front/                           Reservado para la v2 (workspace Angular); no se crea en HU-00
└── .github/workflows/ci.yml         Integración continua
```

`Ali` es el prefijo de ensamblados y espacios de nombres. Se escribe `Ali` y no `ALI` porque las guías de nombres de .NET escriben en PascalCase los acrónimos de más de dos letras (como `Xml` o `Json`).

### Proyectos

| Proyecto | Tipo | Referencias | Contenido en HU-00 |
| --- | --- | --- | --- |
| `Ali.Core` | `classlib` | — | Un único tipo mínimo que permita el test de ejemplo (p. ej. `AppInfo.Name`) |
| `Ali.Cli` | `console` | Core | `Main` que imprime nombre y versión y termina con código 0 |
| `Ali.Mcp` | `console` | Core | `Main` vacío que termina con código 0. Sin paquete MCP todavía |
| `Ali.Core.Tests` | xUnit v3 (paquete `xunit.v3`) | Core | Un test de ejemplo que pasa |

Reglas de dependencia (se mantienen en todas las historias):

- `Core` no referencia a ningún otro proyecto de la solución ni a paquetes de MCP, CLI o web.
- `Cli` y `Mcp` solo referencian a `Core`; no se referencian entre sí.
- La lógica de negocio vive solo en `Core` (ADR-0001).

### Propiedades comunes (`back/Directory.Build.props`)

- `TargetFramework`: `net10.0`.
- `Nullable`: `enable`; `ImplicitUsings`: `enable`.
- `TreatWarningsAsErrors`: `true` desde el principio, también en local.
- `LangVersion`: la predeterminada del SDK (no se fija).
- Sin gestión central de paquetes (`Directory.Packages.props`): se introducirá cuando haya varios paquetes.

### SDK (`global.json`, en la raíz)

- `version`: `10.0.300` con `rollForward: latestFeature`. Admite la banda 10.0.3xx o superior dentro de .NET 10 y rechaza .NET 9 y .NET 11.
- `test.runner`: `Microsoft.Testing.Platform`. xUnit v3 lo usa, y el SDK de .NET 10 exige activarlo para `dotnet test` (ver bitácora).
- Está en la raíz y no en `back/` para que aplique igual al ejecutar desde la raíz o desde `back/`.

## 3. Comportamiento esperado

La historia pide que todo funcione "desde la raíz". Como la solución vive en `back/`, este criterio se refina así: los comandos funcionan **desde `back/`** y también **desde la raíz indicando la carpeta** (`dotnet build back`), porque `dotnet` acepta una carpeta que contiene una única solución.

| Comando | Resultado |
| --- | --- |
| `dotnet restore back` | Sin errores |
| `dotnet build back` | Compila los cuatro proyectos sin errores ni avisos |
| `dotnet test back` | Descubre y ejecuta el test de ejemplo; resultado: 1 superado, 0 fallidos |
| `dotnet run --project back/src/Ali.Cli` | Imprime nombre y versión; código de salida 0 |
| `dotnet run --project back/src/Ali.Mcp` | Termina sin salida; código de salida 0 |

No hace falta ningún paso previo: ni variables de entorno, ni herramientas globales, ni Node, ni Angular.

## 4. `.gitignore`

El actual ya excluye `bin/`, `obj/`, `dist/`, `build/` y `node_modules/`. Se añaden las salidas propias de .NET que faltan:

- `TestResults/` (resultados de `dotnet test`).
- `*.user`, `*.suo`, `.vs/` (estado local de Visual Studio).
- `*.binlog` (logs de MSBuild).
- `coverage*.xml`, `coverage*.json` (cobertura, si se activa).

Se actualiza el comentario "se ajustará al stack de la v1".

## 5. Integración continua (`.github/workflows/ci.yml`)

- **Disparadores:** `push` a cualquier rama y `pull_request` hacia `main`.
- **Sistema:** `ubuntu-latest`, que además comprueba que la solución no depende de Windows.
- **Pasos:**
  1. checkout.
  2. `actions/setup-dotnet` leyendo `global.json`.
  3. `dotnet restore back`.
  4. `dotnet build back --no-restore -c Release`.
  5. `dotnet test back --no-build -c Release`.
- **Éxito:** el job falla si falla la compilación o algún test.
- Sin secretos, sin publicación de artefactos y sin despliegue.

## 7. Criterios de aceptación (refinados)

| # | Criterio | Cómo se verifica |
| --- | --- | --- |
| CA-1 | Existen los cuatro proyectos de §2, en `back/src` y `back/tests`, con las referencias indicadas | Inspección de los `.csproj`; `dotnet build back` |
| CA-2 | `Core` no referencia a `Cli` ni a `Mcp`, y estos no se referencian entre sí | Inspección de los `.csproj` |
| CA-3 | `dotnet build back` termina sin errores ni avisos | Ejecución local y en CI |
| CA-4 | `dotnet test back` ejecuta 1 test y pasa | Ejecución local y en CI |
| CA-5 | Tras compilar y probar, `git status` no muestra ficheros generados | Ejecución local |
| CA-6 | El flujo de CI se ejecuta en el push y termina en verde | Pestaña Actions de GitHub |

## 8. Fuera de alcance

- Funcionalidad de negocio, modelo de dominio y lectura de ficheros (HU-01 en adelante).
- Paquete `ModelContextProtocol`, alojamiento genérico (`Microsoft.Extensions.Hosting`) y parseo de argumentos de la CLI: se añaden en la historia que los necesite.
- Carpeta `front/` y proyectos de la v2 (API web, Angular).
- Empaquetado como herramienta global (`dotnet tool`), publicación y versionado: HU-09.
- Análisis estático adicional, cobertura mínima o formateo obligatorio en CI.
