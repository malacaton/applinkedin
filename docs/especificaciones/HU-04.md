# Especificación HU-04: Cambiar el estado de una pieza

- **Historia:** [HU-04](../historias/HU-04-cambiar-estado.md)
- **Estado:** Aprobada
- **Fecha:** 2026-11-14
- **Decisiones aplicables:** [ADR-0002](../decisiones/0002-ficheros-como-fuente-de-verdad.md) (solo se toca el bloque de metadatos), [ADR-0007](../decisiones/0007-yamldotnet-para-metadatos.md)
- **Depende de:** [HU-01](HU-01.md) (lectura del bloque YAML), [HU-03](HU-03.md) (CLI)

## 1. Objetivo

Primera escritura del proyecto. Cambiar `estado`, `fecha_prevista`, `fecha_publicada` y `url` de una pieza, modificando **solo** su bloque YAML y dejando el cuerpo idéntico byte a byte. La lógica vive en el núcleo para que la reutilice el MCP (`cambiar_estado`, HU-08); la CLI añade el comando `ali estado`.

## 2. Uso (CLI)

```
ali estado <fichero> [--contenido <carpeta>] [--estado <estado>]
           [--fecha-prevista <fecha>] [--fecha-publicada <fecha>] [--url <url>]
```

| Opción | Efecto |
| --- | --- |
| `<fichero>` | Ruta de la pieza relativa a la carpeta de contenido, tal como la muestra `ali listar` (`casos/02-memoria.md`). Se admite sin `.md` y con `\` o `/` |
| `--contenido`, `-c` | Igual que en `listar`: opción, después `ALI_CONTENIDO` y por último la carpeta actual |
| `--estado`, `-e` | Nuevo estado: `idea`, `borrador`, `listo`, `programado` o `publicado` |
| `--fecha-prevista` / `--fecha-publicada` | Fecha `AAAA-MM-DD`, o la palabra `hoy` |
| `--url` | URL absoluta `http` o `https` de la pieza publicada |

- Hay que indicar al menos un campo.
- **Salida si hay cambios:**

  ```
  Actualizado casos/02-memoria.md:
    estado: programado → publicado
    fecha_publicada: — → 2026-11-18
  ```

- **Salida si los valores ya eran esos:** `Sin cambios en casos/02-memoria.md.` En ese caso el fichero no se reescribe y su fecha de modificación no cambia.
- **Errores:** se escriben en stderr como `error: <motivo>` y el comando termina con código 1. El fichero queda intacto.

## 3. Reglas de validación

Se comprueban **todas antes de escribir**. Si alguna falla, no se toca el fichero.

| Regla | Mensaje |
| --- | --- |
| Al menos un campo | `Indica al menos un campo que cambiar: --estado, --fecha-prevista, --fecha-publicada o --url.` |
| La pieza existe, es `.md` y está dentro de la carpeta de contenido (no se aceptan `..` ni rutas absolutas fuera de ella) | `No existe la pieza 'x' en <carpeta>.` / `La pieza debe estar dentro de la carpeta de contenido.` |
| Estado válido | El mismo mensaje que en `listar` |
| Fechas válidas | `Fecha 'x' no válida en --fecha-prevista. Formato esperado: AAAA-MM-DD u hoy.` |
| URL absoluta `http`/`https` | `URL 'x' no válida: debe empezar por http:// o https://.` |
| `publicado` exige `fecha_publicada`, ya sea la que se indica ahora o la que ya tenga la pieza; la `url` es opcional | `Para marcar como publicado hace falta --fecha-publicada (la pieza no tiene fecha_publicada).` |
| El bloque YAML existente es válido y está cerrado. Si tiene errores (los avisos de bloque de HU-01), no se escribe | `El bloque YAML de 'x' no es válido (<motivo>); corrígelo a mano antes de cambiarlo.` |

Las demás combinaciones se permiten; por ejemplo, poner `fecha_publicada` sin cambiar el estado. Comprobar la coherencia general es tarea de HU-06.

## 4. Cómo se escribe

### Pieza con bloque YAML

- **Edición por líneas dentro del bloque:** se busca la línea de primer nivel `clave:` de cada campo y se sustituye por `clave: valor`. También se sustituyen sus líneas de continuación (las sangradas o que empiezan por `-`), por si el valor anterior ocupaba varias líneas.
- **Si el campo no existe,** se añade antes de la línea de cierre, en el orden `estado`, `fecha_prevista`, `fecha_publicada`, `url`.
- **Se conserva todo lo demás:** el resto de campos (incluidos los desconocidos), su orden, los comentarios en líneas propias, las líneas vacías y los delimitadores. Si la línea sustituida tenía un comentario al final (`estado: borrador  # revisar`), ese comentario se pierde. Queda documentado como limitación.
- **Formato de los valores:** sin comillas. Los estados y las fechas no las necesitan, y las URL válidas no llevan espacios ni empiezan por caracteres especiales de YAML.

### Pieza sin bloque YAML

- Se crea al principio del fichero, con solo los campos indicados:

  ```
  ---
  estado: listo
  ---
  ```

- El contenido original queda a continuación, intacto. No se añade `serie`: la pieza sigue sin clasificar hasta que se asigne una a mano o desde HU-07.

### Garantías comunes

- **Cuerpo intacto:** todos los bytes posteriores a la línea de cierre del bloque (o el fichero entero, si no había bloque) se copian sin cambios.
- **BOM y saltos de línea:** se conserva el BOM UTF-8 si lo había. Las líneas nuevas usan el mismo salto que el fichero (`\r\n` o `\n`, según el primer salto que aparezca); si no hay ninguno, `\n`.
- **Comprobación antes de guardar:** el bloque nuevo se vuelve a interpretar con el lector de HU-01. Si los campos escritos no dan exactamente los valores pedidos, no se guarda y se informa del error. Es una red de seguridad que no debería saltar nunca.
- **Escritura segura:** se escribe en un fichero temporal de la misma carpeta y se sustituye el original. Si algo falla a mitad, el original queda como estaba.
- **Sin cambios, sin escritura:** si todos los valores pedidos coinciden con los actuales, no se escribe.

## 5. Núcleo

```
PieceChanges     = { Status?, PlannedDate?, PublishedDate?, Url? }        (null = no cambiar)
PieceUpdater.Update(string rootPath, string piecePath, PieceChanges) → PieceUpdateResult
PieceUpdateResult = { Path, Before: Piece, After: Piece, Changes: FieldChange[] }   (vacío = sin cambios)
FieldChange      = { Field, OldValue?, NewValue }
PieceUpdateException(message)                                           (cualquier regla de §3)
```

La palabra `hoy` la resuelve la CLI con su reloj, que en los tests es inyectable. El núcleo solo recibe fechas.

## 6. Criterios de aceptación (refinados)

| # | Criterio | Prueba |
| --- | --- | --- |
| CA-1 | Se cambian `estado`, `fecha_prevista`, `fecha_publicada` y `url`, por separado y juntos, y la relectura con HU-01 da los valores nuevos | Tests del núcleo |
| CA-2 | El cuerpo queda idéntico byte a byte, con y sin BOM y con `\n` y `\r\n` | Comparación de bytes del cuerpo antes y después |
| CA-3 | El resto del bloque se conserva: otros campos, campos desconocidos, comentarios en líneas propias y orden | Test que compara el bloque línea a línea |
| CA-4 | Sin bloque YAML, se crea al inicio y el contenido original queda detrás sin cambios | Test |
| CA-5 | `publicado` sin `fecha_publicada` (ni indicada ni existente) se rechaza; con fecha existente se acepta | Tests |
| CA-6 | Estado, fecha, URL o ruta inválidos, o bloque YAML roto, se rechazan sin modificar el fichero (mismos bytes y misma fecha de modificación) | Un test por caso |
| CA-7 | Si no hay cambios, no se escribe | Fecha de modificación sin cambios |
| CA-8 | `ali estado` muestra los cambios, admite `hoy` y da código 0; con error, código 1 y mensaje en stderr | Tests de la CLI |

## 7. Fuera de alcance

- Borrar campos (por ejemplo, quitar una `url`): se hace a mano en el fichero.
- Cambiar `serie`, `depende_de` o `formato` (la serie se asigna al crear la pieza, HU-07).
- Conservar el comentario al final de una línea que se sustituye.
- Cambiar varias piezas de una vez.
- Historial de cambios: lo da Git si el usuario versiona su carpeta (ADR-0002).

## 8. Decisiones de la revisión

| Pregunta | Decisión |
| --- | --- |
| `hoy` como valor de fecha | Se admite en `--fecha-prevista` y `--fecha-publicada` |
| Borrar campos | Fuera de alcance; se hace a mano |
| Comentario al final de una línea sustituida | Se pierde; queda documentado como limitación |
