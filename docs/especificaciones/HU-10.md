# Especificación HU-10: Skill de ejemplo

- **Historia:** [HU-10](../historias/HU-10-skill-ejemplo.md)
- **Estado:** Aprobada
- **Fecha:** 2026-11-15
- **Decisiones aplicables:** [ADR-0005](../decisiones/0005-ia-fuera-del-nucleo.md) (el criterio editorial se entrega como skill, no en el núcleo)
- **Depende de:** [HU-08](HU-08.md) (herramientas MCP), [HU-09](HU-09.md) (manual)

## 1. Objetivo

Dar al asistente de IA, en una skill reutilizable, dos cosas: **cómo usar** las cinco herramientas de appLinkedIn y **qué criterios editoriales** seguir al proponer o revisar piezas. Así el usuario no tiene que repetirlo en cada conversación. Es contenido, no código: el núcleo no cambia.

## 2. Estructura

```
skill/
└── planificar-publicaciones/
    ├── SKILL.md                    Cuándo y cómo usar las herramientas; flujos de trabajo
    └── criterios-editoriales.md    Criterios de ejemplo, PERSONALIZABLES
```

- **Formato estándar de skill:** una carpeta con `SKILL.md`, que lleva un bloque YAML con `name` y `description`, y ficheros de apoyo que el asistente lee solo cuando los necesita.
- **Dos ficheros separados:** las instrucciones de uso (que dependen de la herramienta) y los criterios (que dependen de cada persona). Así, para adaptar la skill basta con editar `criterios-editoriales.md`.
- **Contenido genérico:** sin datos personales, empresas ni ejemplos reales (CLAUDE.md).

## 3. `SKILL.md`

**Bloque YAML:**

- `name: planificar-publicaciones`.
- `description`: cuándo activarla. Por ejemplo, al planificar, revisar o crear publicaciones o artículos de una serie, al buscar fechas libres o al marcar una pieza como publicada, siempre que el servidor MCP `applinkedin` esté conectado.

**Cuerpo:**

1. **Qué es appLinkedIn:**
   - El catálogo es local; los ficheros `.md` son la fuente de verdad.
   - No publica en LinkedIn: la publicación y la programación las hace la persona, con el programador nativo.
2. **Cuándo usar cada herramienta:**

   | Herramienta | Cuándo |
   | --- | --- |
   | `listar_piezas` | Para saber qué hay, antes de proponer nada |
   | `buscar_huecos` | Para proponer fechas; nunca se inventan |
   | `validar_calendario` | Para revisar el plan, antes y después de cambiarlo |
   | `cambiar_estado` | Para marcar avances (borrador → listo → programado → publicado) |
   | `crear_pieza` | Para crear el fichero de una idea nueva |

3. **Reglas de uso:**
   - **Fechas:** se proponen solo las que devuelve `buscar_huecos` (o `crear_pieza` con `fecha_libre`).
   - **Escrituras:** antes de cada escritura (`cambiar_estado`, `crear_pieza`) se resume qué va a cambiar y se pide confirmación. La excepción es que la persona lo haya pedido de forma explícita.
   - **Publicado:** marcar como publicado exige `fecha_publicada`; se pide la URL si no se tiene.
   - **Problemas:** los que devuelva `validar_calendario` se explican en lenguaje llano, con una propuesta de arreglo para cada uno.
   - **Errores de herramienta:** se leen y se corrigen; no se reintenta igual.
   - **El texto de la pieza:** la herramienta solo toca el bloque YAML. Si la persona pide redactar o corregir el texto, el asistente propone el texto en la conversación y no edita el fichero.
4. **Flujos típicos:** cada flujo lista sus pasos, en este orden de herramientas:
   - **Planificar las próximas semanas:** `validar_calendario` → `buscar_huecos` por serie → propuesta → `crear_pieza`.
   - **Tengo una idea:** elegir la serie y el título → `crear_pieza` con `fecha_libre`.
   - **Ya lo publiqué:** `cambiar_estado` con `publicado`, `fecha_publicada` y `url`.
   - **Revisar un borrador antes de darlo por listo:** aplicar `criterios-editoriales.md` → `cambiar_estado` a `listo`.
5. **Criterios editoriales:** se leen de `criterios-editoriales.md` al redactar o revisar. Si chocan con lo que pida la persona, manda la persona.

## 4. `criterios-editoriales.md`

Lleva un aviso claro al principio: *"Ejemplo. Adáptalo a tu estilo: todos los valores son orientativos y personalizables."*

| Apartado | Ejemplo de contenido |
| --- | --- |
| Publicación (`post`) | Gancho en las 2 primeras líneas (antes del "ver más", unos 200 caracteres). Entre 800 y 1.300 caracteres. Párrafos cortos. Una sola idea. Cierre con una pregunta o una llamada a la acción |
| Artículo (`articulo`) | Entre 800 y 1.500 palabras. Título claro con la promesa. Entradilla de 2 o 3 frases. Intertítulos cada 200 o 300 palabras. Conclusión práctica |
| Carrusel (`carrusel`) | Entre 6 y 10 tarjetas. Una idea por tarjeta. Portada con la promesa. Última tarjeta con el resumen |
| Etiquetas | Entre 3 y 5, específicas, al final |
| Tono | Cercano y concreto; ejemplos antes que teoría; sin jerga innecesaria |
| Series | Qué es cada serie y su propósito. Las del ejemplo (casos reales, fundamentos, resumen de un caso y notas) se explican en una línea cada una, como modelo |
| Calendario | Preferencia: no publicar dos piezas el mismo día, aunque la herramienta lo permita. Dejar al menos un día entre series distintas |
| Lista de revisión | Comprobaciones antes de marcar `listo`: gancho, longitud, una idea, sin erratas, enlaces revisados |

Las cifras son orientativas y se presentan como preferencias de ejemplo, no como reglas de LinkedIn.

## 5. Manual (HU-09)

Se añade una sección **"11. Skill de ejemplo"** a `docs/manual.md`:

- **Qué hace:** qué aporta la skill y dónde está.
- **Instalar en Claude Desktop:**
  - Comprimir la carpeta `planificar-publicaciones` en un `.zip`. Para ello se dan los comandos de PowerShell (`Compress-Archive`) y de macOS (`zip -r`).
  - Subir el `.zip` en **Configuración → Capacidades → Skills**.
- **Instalar en Claude Code:** copiar la carpeta a `~/.claude/skills/`, o a `.claude/skills/` del proyecto.
- **Adaptarla:**
  - Editar `criterios-editoriales.md`: longitudes, tono, descripción de tus series y preferencias de calendario.
  - Volver a subirla tras cada cambio.
- **Comprobar que se activa:** pedir "Planifica mis próximas dos semanas" y ver que el asistente empieza por `validar_calendario` y `buscar_huecos`.

## 6. Pruebas

Como es contenido, se prueba su **coherencia con el servidor**. Va en `Ali.Mcp.Tests`, en un test `ExampleSkillTests`, que comprueba:

- **Bloque YAML de `SKILL.md`:**
  - Tiene `name` y `description`.
  - `name` usa solo minúsculas, dígitos y guiones, y no pasa de 64 caracteres.
  - `description` no está vacía y no pasa de 1.024 caracteres.
- **Herramientas citadas:**
  - Las cinco herramientas del servidor aparecen en `SKILL.md`.
  - `SKILL.md` no cita ninguna herramienta (`xxx_yyy` entre comillas invertidas) que no exista en el servidor.
  - Los parámetros que cita (`fecha_libre`, `fecha_publicada`…) existen en la herramienta correspondiente.
- **Enlaces:** `SKILL.md` enlaza `criterios-editoriales.md` y el fichero existe.
- **Manual:** el manual menciona la carpeta de la skill.

## 8. Fuera de alcance

- Varias skills (por formato o por serie).
- Generar texto con IA desde la herramienta (ADR-0005).
- Empaquetar el `.zip` automáticamente en la CI o en una versión publicada.

## 9. Decisiones de la revisión

| Pregunta | Decisión |
